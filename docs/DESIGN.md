## 1. 背景与痛点

竞赛 / 活动报名、信息采集等场景普遍采用**在线协作表格**（腾讯文档、飞书表格、石墨、Google Sheets、Excel Online 等）。表格回收后，组织者面临同一类问题：**多人填写导致格式不一致**，整理工作耗时且易出错。

典型症状：

1. **日期格式五花八门**：`2024/1/5`、`2024年1月5日`、`01-05-2024`、`2024.01.05`、`1/5` 混用，无法直接排序、筛选或做透视。
2. **数字串被意外解析为科学计数法**：学号、手机号、身份证号、订单号等长数字串被表格软件转成 `2.02401E+16`，**且精度已经丢失**，肉眼无法还原原值。
3. **下拉选择列被手动输入**：单元格本应从下拉选项取值，却填了 `男` / `男 ` / `Male` / `M` / `男生` 等变体，与选项集合对不上，导致统计口径不一致。
4. **单元格首尾存在非预期格式符**：前后空格、全角空格、不换行空格、零宽字符、换行符、残留引号等，导致精确匹配失败。

这些问题的共同特征：**单条看都能人工修，量大且混杂时人工几乎不可行**；同时**不能盲目改**——误改语义比不修改更糟。因此需要一套以「AI 自主判断」为核心、以「处理流程 + 判断规则」为载体的 Skill。

---

## 2. 目标与非目标

### 2.1 目标

- 把「回收后的脏表格」整理为「格式统一、可直接用于统计的干净表格」。
- 支持**全部主流电子表格格式**，由 AI 根据输入文件自行选择处理方式。
- 对每一处改动**可追溯、可审计**（变更报告）。
- 对**无法确定**的情况**主动交给用户决策**，而不是猜测或静默处理。
- 以 **AI Skill** 形式交付：Skill **只提供处理流程与判断规则**，不附带处理脚本；AI 借助自身可用的工具/库完成读写与判断。
- **回复语言**：用户期望用什么语言，就用那种语言；由调用方 AI 自行决定，Skill 不作硬性限定。

### 2.2 非目标（本期不做）

- 不修改表格的**业务语义**、不补全缺失的业务数据（如凭空编造电话号码）。
- 不做跨表合并、去重、透视分析（后续版本考虑）。
- 不处理图片、图表、宏等复杂对象；不重写公式。
- 不直接覆盖用户原始文件（始终另存副本）。
- 不捆绑任何 Python/Node 处理脚本或第三方库作为 Skill 的一部分（工具由 AI 自身环境提供）。

## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| **列类型（column type）** | 每列被 AI 推断或确认的语义类型：`date`（日期）、`id`（标识数字串）、`number`（数值）、`choice`（下拉选择）、`text`（自由文本）。 |
| **例子行（example row）** | 表格中格式明显正确、可作为该列格式标杆的已有单元格。日期目标格式优先取例子行的样式。 |
| **选项集合（option set）** | 仅当输入表格自身配置了下拉/数据验证选项时存在；作为 `choice` 列对齐的合法取值依据。 |
| **处理策略** | 对每处异常，按置信度分为 `auto`（自动修复）、`review`（待用户确认）、`report`（仅报告不改）。 |
| **置信度（confidence）** | AI 对「这次修复是否正确」的把握，决定走上述哪种策略。**完全由模型自主判断**。 |
| **变更报告（change log）** | 记录每个单元格的：`原值 → 新值 → 规则 → 置信度 → 策略`。 |

## 4. 总体设计

### 4.1 设计原则

1. **纯流程 Skill**：Skill 只规定「怎么做、怎么判断」，不提供「用什么脚本做」。AI 根据输入格式自主选择工具完成读写。
2. **模型自主判断**：所有列类型推断、格式识别、语义匹配、置信度判定均由调用 AI 完成，不依赖硬编码规则引擎。
3. **最小改动**：能不改就不改；只动明确异常的单元格。
4. **不破坏语义**：任何可能改变含义的修复都必须经用户确认（`review`）。
5. **可逆与可审计**：始终保留原文件副本与逐单元格变更记录，一键可回退。
6. **幂等**：同一份脏表格跑两次，第二次不产生新改动。
7. **人机分工**：AI 判断 + 用户决策；拿不准的就问，不硬猜。

### 4.2 格式支持（AI 自主适配）

Skill 不绑定具体格式，要求 AI 根据输入文件自行选择可用工具/库处理，至少覆盖：

- `xlsx` / `xlsm`（Excel 工作簿，含数据验证规则）
- `xls`（旧版 Excel）
- `csv` / `tsv`（注意 GBK / UTF-8 / UTF-8-BOM 编码检测）
- `ods`（OpenDocument 表格）
- 在线协作表格导出文件（腾讯文档 / 飞书 / 石墨 / Google Sheets 等导出的上述格式）

> AI 应根据环境实际可用的工具（如编程语言与表格库）自行选择；Skill 不规定具体实现，也不捆绑实现。

### 4.3 处理流程（Pipeline）

```
输入文件（任意主流电子表格格式）
   │
   ▼
① AI 读取表格：识别格式、工作表结构、表头、数据验证规则、单元格类型与显示值
   │  （工具由 AI 自选；本 Skill 不提供脚本）
   ▼
② 列类型推断：AI 对每列推断类型；歧义时问用户
   │
   ▼
③ 确定日期目标格式：若该列存在格式正确的「例子行」则以其为准，否则用 YYYY-MM-DD
   │
   ▼
④ 确定选项集合：仅当输入表格配置了下拉/数据验证选项时读取；否则按 §5.3 处理
   │
   ▼
⑤ AI 逐列逐单元格检测异常并自主判断置信度 → 分配 auto / review / report
   │
   ▼
⑥ 汇总「待确认清单」→ 一次性向用户提问（避免逐个打断）
   │
   ▼
⑦ AI 应用所有 auto 修复 + 用户已确认的 review 修复，另存副本
   │
   ▼
⑧ 输出：整理后的文件 + 变更报告 + 待确认/未解决清单
   │
   ▼
⑨ 以「用户期望的语言」回复（由调用 AI 决定）
```

### 4.4 置信度与处理策略（模型自主判定）

| 置信度 | 策略 | 行为 |
| --- | --- | --- |
| 高（格式确定 / 语义唯一匹配） | `auto` | 直接修复，记入变更报告 |
| 中（多种可能，但有明显首选） | `review` | 在待确认清单中列出「建议值 + 备选」，用户一键采纳或改写 |
| 低（无法判断） | `report` | 不修改，仅记录并提示用户自行处理 |

> 激进度（保守 / 平衡 / 激进）由 AI 根据场景自行把握，倾向保守：任何改变语义的修复都应确认。

## 5. 核心能力详述

> 以下各节是**给 AI 的判断指引**，不是固定算法。AI 应结合表格上下文自主判断，并在变更报告中说明依据。

### 5.1 日期规范化

**目标格式判定（按顺序）**：

1. 若该列有**格式正确、可作为标杆的例子行**（如整列多数为 `2024/09/01` 且含义明确），则**照例子行的格式**统一，不强行改成 ISO。
2. 若没有可参考的例子行，或例子行本身歧义/混乱，则**统一为 `YYYY-MM-DD`**（ISO 8601，可排序、无歧义）。

**识别范围**：`2024/1/5`、`2024.1.5`、`2024年1月5日`、`2024-01-05`、`01/05/2024`、`05-01-2024`、`Jan 5, 2024`、Excel 序列号日期等。

**判断要点（AI 自主）**：

| 情况 | 建议策略 |
| --- | --- |
| 年月日齐全且无歧义 | `auto` 转为目标格式 |
| 有歧义（如 `01/02/2024`） | `review`：按例子行推断顺序；无例子行则问用户该列日期顺序，列出候选 |
| 缺年份（如 `1/5`） | `report`，提示补全年份；若上下文可可靠推断年份可 `review` |
| 非法日期（如 `2024-02-30`） | `report`，不猜测 |
| 已是目标格式 | 不动（幂等） |

**要点**：歧义优先在**列级别**统一决策（问一次「这列是什么顺序」），而非逐格询问。

### 5.2 科学计数法与数字串

**核心判断**：区分「本应是标识符的长数字串」与「本身就是数值的科学计数法」。由 AI 结合列上下文自主判断。

**识别信号**：

- 显示格式为科学计数法（`1.23E+10`）。
- 长连续数字串（如 ≥ 11 位）或符合特定模式（手机号、身份证号、固定长度学号等）。
- 精度是否可能已丢失：还原后尾数是否为「整齐 0 结尾」或无法匹配任何合法标识符模式 → 提示精度风险。

**判断要点（AI 自主）**：

| 情况 | 建议策略 |
| --- | --- |
| 整列多数为长数字串标识符，个别显示为科学计数法 | 判定 `id` 列；可还原的恢复为纯文本（按例子行/列惯例保留前导零）；**精度已丢失则 `report` 明确警告需回原始来源核对** |
| 形如 `1.5e5`、`3.2E-4` 且有数值列上下文 | 判定为合法数值，保留或展开为普通小数，`review` |
| 无法确定 | `review`，展示原值、显示值、推断类型与理由 |
| 普通短数字 | 不动 |

> **红线**：长数字转 double 后科学计数法显示时**精度通常已不可逆丢失**。AI 绝不能声称「已恢复原值」——只能恢复格式，并对精度风险明确警告。

### 5.3 下拉选择列对齐

**选项集合来源（严格限定）**：**仅**取输入表格自身配置的下拉/数据验证选项。若表格未配置选项，则不构造外部/用户提供的选项集；此时 AI 应根据该列上下文（高频值、语义聚类、表头含义）自主判断是否存在应统一的类别，拿不准的列入 `review`/`report` 并说明原因。

**步骤（AI 自主）**：

1. 读取表格中配置的下拉选项；若无配置则按上段处理。
2. 对每个疑似手动输入值，与选项集合比较（字面归一化 + 同义词/语义，如 `男↔Male↔男生`、`是↔Y↔Yes`）。
3. 按置信度分级：

| 最高匹配程度 | 建议策略 |
| --- | --- |
| 归一化后完全相等（仅差空格/全角） | `auto` 修复 |
| 较高且明显领先（如 `Male`→`男`） | `review`，建议值 + 理由 |
| 与多个选项接近、难分 | `report`/`review`，明确告知无法确定 |
| 无相近选项 | `report`，提示可能是新增类别，问是否加入选项集 |

> 关键约束：**绝不**在没有把握时把一个选项强行改成另一个，尤其当两者语义不同（如 `否` 改成 `是`）。

### 5.4 首尾格式符清理

**目标**：清除单元格首尾的非预期字符，不影响内部正常内容。

**清理清单**（默认开启，AI 可按需调整）：

- 半角空格、全角空格 `　`、不换行空格 `\u00A0`、制表符 `\t`、换行符 `\n`/`\r`。
- 零宽字符：`\u200B`、`\u200E`、`\u200F`、`\uFEFF`（BOM）等。
- 成对的残留引号、Excel 强制文本的前导 `'`。
- 其他不可见控制字符（Unicode `Cc` 类）。

**判断要点**：通常是**高置信度、纯格式性** → `auto`。若清理后会命中下拉选项匹配，则并入 §5.3 流程。**只清理首尾，不触碰内部**（避免破坏编号中的连字符等有意内容）。

## 6. AI 自主处理（无自带脚本）

本 Skill **不提供任何处理脚本或第三方库**。AI 在运行时：

- 根据自身环境可用的工具（如编程语言、表格库、命令行）自行读写目标格式。
- 用自身判断力完成列类型推断、例子行识别、语义匹配、置信度评估。
- 用自身能力生成整理后的文件与变更报告（写文件工具由 AI 环境提供）。

Skill 的价值在于**标准化的处理流程与判断规则**，确保不同 AI / 不同次运行结果一致、可审计，而不是提供可执行代码。

│   └── pending-template.md   # 待确认清单模板

**SKILL.md frontmatter 示例**：

```yaml
---
name: tabcurate
description: 整理多人填写的线上表格，统一日期/数字/选项/首尾格式符。当用户提供回收的表格并要求"整理/清洗/统一格式"时使用。Skill 只给流程与判断规则，由 AI 自主选择工具处理任意主流表格格式。
---
```

**SKILL.md 语言指引**：回复时使用用户期望的语言，由调用 AI 根据对话判断，Skill 不作硬性限定。

## 8. 输出物

每次运行产出三样东西：

1. **整理后的文件**：`*_cleaned.<原格式>`（原文件保持不变）。
2. **变更报告**（`change-report.md` / `.csv`）：逐条列出 `位置 | 原值 | 新值 | 规则 | 置信度 | 策略` 及汇总统计。
3. **待确认清单**：集中列出所有 `review` / `report` 项，供用户一次性处理；确认后可增量重跑。

所有输出使用**用户期望的语言**（由调用 AI 决定）。

---

## 9. 交互设计

- **先问列、后问格**：列类型与列级策略（日期顺序、选项集）先确认，再处理单元格。
- **批量而非逐个**：所有需要用户决策的项合并成一次提问。
- **给理由与建议**：每个待确认项说明「为什么拿不准」以及「建议值与备选」。
- **可中途退出**：用户可只处理高置信度项，其余保留原样。

---

## 10. 安全与边界情况

- **绝不覆盖原文件**；写入前校验副本路径。
- **精度丢失不可逆**：科学计数法场景必须显式警告，不作虚假承诺（§5.2 红线）。
- **保留公式**：默认不改动含公式的单元格；如需处理需用户明确授权。
- **超大文件**：采样推断 + 分块处理，避免内存溢出；报告分节。
- **多工作表**：逐表独立推断列类型。
- **编码问题**：csv 自动检测 GBK/UTF-8/UTF-8-BOM。
- **语言不确定时**：由调用 AI 根据用户表述自行决定；不默认强制中文。

## 11. 示例演示

**输入片段**（某报名表）：

| 姓名 | 出生日期 | 学号 | 性别 | 备注 |
| --- | --- | --- | --- | --- |
| ` 张三` | `2003/9/1` | `2.02301E+17` | `男` | `OK（` |
| `李四` | `2003年9月1日` | `202309010012` | `Male` | `合格 ` |

**AI 处理**：

- `姓名`：`" 张三"` → `"张三"`（`auto`，首尾空格）。
- `出生日期`：列有例子行 `2003/9/1` → 按其样式统一为 `2003/9/1`（若判定例子行歧义/不统一，则用 `2003-09-01`）。出现 `01/02/2004` 则 `review` 问日期顺序。
- `学号`：判定为 `id` 列；`2.02301E+17` 精度已丢失 → `report` 警告；`202309010012` 按列惯例保留为文本/前导零。
- `性别`：表格配置了选项 `['男','女']`；`Male` → 建议 `男`（`review`，理由：语义等价）。若表格未配置选项，则不构造选项集，按列上下文判断并给出建议或 `report`。
- `备注`：仅清理首尾 → `report` 提示人工核对（`OK（` 尾部残括号含义不明，不动内部）。

**输出**：干净文件 + 报告（含 1 条精度警告、1 条待确认建议），以用户期望的语言回复。

## 13. 开放问题（待与用户确认）

1. 日期「例子行」的判定标准：是否要求该列多数行格式一致才算标杆？
